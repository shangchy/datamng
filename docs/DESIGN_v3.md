# 嘟嘟数据管理系统 · 重设计方案 v3

> 日期：2026-09-10 ｜ 提出：BOSS ｜ 设计：护卫
> 目标：把「每天上游收到的甲方数据 + 分发给代理的数据 + 中间损耗」全部变成可查、可追溯、可分析的数据资产
> 状态：**待 BOSS 确认后实施**

---

## 一、现状盘点（实测数字，2026-09-10）

| 项目 | 现状 |
|---|---|
| 库 | SQLite `~/dudu-system/data/dudu.db`，856MB，33 表 |
| 交付明细 | `daily_records` **227.2 万行**（8/24、8/30~9/9），含 日期/上游/代理/任务/渠道/手机号/平台/省/市/姓名 |
| 上游原始 | `upstream_raw` **66.4 万行**（8/22~8/9 各日全量逐行，含被剔除行） |
| 交付汇总 | `fact_delivery` 4820、`fact_bill` 239、`bill_daily` 147、`agent_daily_price` 231 |
| 财务 | `fact_balance` 126、`fact_wash` 37、`wash_cost` 12、`agent_recharges` 21 |
| 手机号索引 | `daily_records.phone` 已建索引；`phone_name_index` 12.7 万（洗名姓名） |
| 公积金库 | `gongjijin_lib` 38.8 万行（带姓名/单位，可做身份富化） |

### 对照你的 4 条需求 → 缺口

| 需求 | 现有基础 | 缺口 |
|---|---|---|
| ① 每天来了哪些数据、明细 | upstream_raw 已有逐行原始 | 缺「文件级台账」视图（谁、几点、哪个文件、多少行） |
| ② 数据流向（发给谁/重复剔除/积压） | daily_records 有交付去向 | **剔除与积压没有任何记录**；上游↔交付只能靠 phone+日期反查（实测 9/9 匹配率 **98.7%**，可用） |
| ③ 手机号全息查询 | `/api/phone` 只有「交付侧」 | 缺供给侧（哪天哪个甲方给的）、缺剔除原因、无时间线视图 |
| ④ 经营趋势（需求/供货/营收/资产） | 营收侧（bill_daily/fact_bill）可复用 | **需求侧完全没入库**（提单表未进 DB）；无周/月聚合；**无业务领域维度、无资产台账** |

## 二、总体架构（三层，不推倒重来）

```
采集层（每日 ETL，幂等可补跑）
  上游文件 → upstream_raw     （已有）
  交付文件 → daily_records    （已有）
  提单表   → fact_demand      （新增）
  剔除/积压→ fact_drop / fact_backlog（新增，需流程配合产出明细）
  维度映射 → dim_platform / dim_vertical（新增，人工维护）
        ↓
主题层
  血缘：v_phone_timeline（供给∪交付∪剔除∪洗名 事件流）
  经营：fact_supply / fact_demand / fact_delivery / bill_daily
  资产：asset_platform_daily / asset_vertical_summary
        ↓
展示层（Flask 页面，本机 127.0.0.1:5000）
  P0 数据流向 · P1 手机号全息 · P2 经营趋势 · P3 数据资产 · P4 维护
```

**技术选型建议**：继续 SQLite + Flask。
理由：单机、单用户、无并发；227 万行查询 <50ms；换 Postgres 只增加运维成本。
配套：明细表按季度归档（`daily_records_y2026q3` 之类），汇总表永久保留，避免单表过亿。

## 三、数据模型（v3 新增 10 张表）

### 1. `event_phone` —— 手机号事件流（血缘核心）
> 展示层用 UNION 视图，实体表只落「新增的两类事件」（剔除/积压），避免重复存储 300 万行

| 字段 | 说明 |
|---|---|
| phone | 手机号（索引） |
| biz_date | 业务日期 |
| event | `供给` / `交付` / `剔除` / `积压` / `洗名` / `区域剔除` |
| upstream_id | 哪个甲方（牛/新） |
| agent_id | 交付给谁（供给/剔除事件可为空） |
| channel_id / task_id / platform_id | 渠道 / 任务 / 平台 |
| province / city | 省市 |
| file_id | 来源文件 |
| reason | 剔除原因：任务内重复 / 平台库重复 / 大库重复 / 区域限制(京津) / 排除任务(教育ABC) / 待处理 |
| created_at | 记录时间 |

视图 `v_phone_timeline`：`upstream_raw`（供给）∪ `daily_records`（交付）∪ `event_phone`（剔除/积压）→ 按 phone+日期 排序即得完整时间线。

### 2. `fact_demand` —— 需求台账（来自每日提单表）
日期 / 甲方(牛|新) / 代理 / 任务 / 渠道类型 / 运营商 / 数量 / 时长 / 省 / 地市 / url / 工单号 / 状态(在执|停单|改单)
→ 支撑「代理需求量趋势」「领域需求量趋势」

### 3. `fact_supply` —— 供货台账（甲方 × 文件 × 任务 × 平台）
日期 / 甲方 / 来源文件 / 任务 / 平台 / 渠道 / 省市 / 原始量 / 去重后量
→ 支撑「甲方供货趋势」「去重率趋势」

### 4. `fact_drop` —— 剔除明细（手机号级，含总量汇总）
日期 / 手机号 / 甲方 / 任务 / 平台 / 撞库层(任务内|平台库|大库) / 原因 / 目标代理

### 5. `fact_backlog` —— 积压台账
日期 / 甲方 / 任务 / 收进量 / 已交付 / 积压量 / 原因 / 后续补发日期 / 状态

### 6. `dim_platform` —— 平台主数据
平台名 → 领域 / 品类 / 首次出现日 / 是否活跃（人工维护 + 自动兜底）

### 7. `dim_vertical` —— 业务领域
初稿：银行 / 消金信贷 / 保险 / 汽车车主 / 教育 / 电商消费 / 彩票体育 / 生活服务 / 房产权属 / 医疗健康 / 其他

### 8. `asset_platform_daily` / `asset_vertical_summary` —— 资产台账
日期 × 平台/领域：新增独立手机号 / 累计独立 / 重复率 / 交付率 / 洗名命中率 / 复用代理数

### 9. `file_registry` —— 全量文件台账（谁、哪个文件、何时到、多少行、入库状态）
（现有 `upstream_files` 只覆盖上游，扩展成统一登记）

### 10. `dim_calendar` —— 日历（周/月/工作日口径统一）

## 四、页面设计（5 个页签）

### P0 · 数据流向
- **批次总览**：选日期 → 上游文件清单（甲方/文件/行数/到达时间）→ 该批任务 → 分代理交付量 → 去重损耗 → 积压量，一屏看完
- **数量守恒校验**：收进 = 交付 + 剔除 + 积压，不平时红字告警
- **任务流向表**：任务 → 平台 → 渠道 → 代理 → 数量 → 状态（在执/停/改）

### P1 · 手机号全息（你要的"查一个号的全貌"）
输入手机号（每个页面顶部常驻搜索框）→ 输出：
1. **时间线**：`2026-08-30 供给(甲方新/任务A/平台X)` → `2026-08-31 交付(660009/移动-白)` → `2026-09-02 剔除(大库重复)` → `09-03 交付(660005/电信-白)` …
2. **身份卡**：洗名姓名 / 公积金库命中（单位、地区）
3. **汇总**：首次出现日、末次出现日、出现次数、涉及甲方数、代理数、任务数、平台数、是否重复利用
4. **价值标记**：被 ≥2 个代理使用 = 高复用；被剔除次数多 = 低质

### P2 · 经营趋势
- 粒度切换：**日 / 周 / 月**，区间自选
- 三条曲线：**需求量**（提单）／**供货量**（甲方来的）／**交付量**（发出去的）
- 财务曲线：营收 / 成本 / 利润（复用 bill_daily，含洗名费）
- 维度下钻：代理 / 甲方 / 领域 / 渠道 / 运营商
- 缺口分析：需求−交付（未满足）、供货−交付（损耗+积压）

### P3 · 数据资产
- 资产总览：独立手机号总量、今日新增、按领域/平台分布、库龄分布
- 质量：重复率、洗名命中率、有效率
- 复用分析：一手机号被几个代理用过（复购/复用率）→ 价值分层
- 增量趋势：每天新增多少"干净"手机号

### P4 · 维护（现有明细/维护页扩展）
维度维护（平台→领域映射）、文件台账、补跑 ETL、对账报告

## 五、每日 ETL（收工后自动跑，幂等）

1. 文件登记（file_registry）
2. 上游原始入库（已有 `archive_ingest.py`）
3. 交付入库（已有 `importer.py`）
4. **剔除/积压入库**（新增：`daily_pipeline.py` 需输出 drop/backlog 明细清单）
5. **需求入库**（新增：解析当日 提单表 + 停单表 + 改单表）
6. 维度映射（平台→领域，人工维护 + 兜底「其他」）
7. 汇总重建（fact_supply / fact_demand / asset_* / 指标视图）
8. 校验：数量守恒 + 与账单/利润表对账 → 不平则告警，不静默

> 幂等：`--date YYYY-MM-DD` 可单独补跑任意一天，重复跑结果一致。

## 六、分期实施

| 阶段 | 内容 | 预估 |
|---|---|---|
| **P0** | 血缘打通（供给↔交付↔剔除↔积压）+ 手机号全息页 + 批次流向总览 | 1.5 天 |
| **P1** | 经营趋势（需求/供货/交付/财务，日周月） | 1.5 天 |
| **P2** | 数据资产台账（领域/平台/复用） | 1 天 |
| **P3** | 历史回填（8/22 起）+ 索引与性能优化 + 归档策略 | 0.5~1 天 |

**回填可行性（重要）**：
- 交付/供给明细：可回填到 8/22（有 upstream_raw + daily_records）✅
- **剔除/积压明细：过去没留痕，无法精确回填**，历史只能给"总量差额"估算；从实施后每天记全 ⚠️
- 需求（提单表）：桌面 每日提单表/ 有 0830~0909 历史文件，可全部回填 ✅

## 七、需要 BOSS 拍板的 8 件事

1. **需求口径**：提单表 = 代理需求台账，对吗？（数量是"代理要多少"）
2. **停单/改单**是否也入 demand 表（我建议入，带状态，趋势才完整）
3. **剔除明细留档**：每天多存约 5~15% 行（估 5k~10k 行/天），换来"为什么这个号没发出去"——要吗？（我建议要）
4. **积压定义**：上游收进 − 实际交付 = 积压，包含被排除任务/区域限制，对吗？
5. **领域分类表**：我按平台名起草一版（银行/消金/保险/汽车/教育/电商/彩票…），你审改
6. **历史回填范围**：8/22 起（含老牛期，只有数量无金额）——够吗？
7. **技术选型**：继续 SQLite（推荐，单机够用）
8. **增长预期**：按 5 万行/天明细，年增约 3000 万行 → 建议明细按季度归档 + 汇总永久保留（约 1~2 年后单表过亿，必须做，否则查询变慢）

## 八、风险与对策

| 风险 | 对策 |
|---|---|
| 剔除/积压历史无明细 | 接受不可回填，从实施日起记全；历史只做总量差 |
| DB 年增 3000 万行 | 季度归档 + 汇总表永久；phone 索引必留 |
| 平台→领域映射失真 | 人工维护 + 页面可改，兜底"其他"，不静默猜 |
| 流程改动（pipeline 要输出 drop 明细） | 改 `daily_pipeline.py` 输出 drop/backlog JSON，收工时随 ETL 入库 |
| 分渠道错分等老问题 | ETL 校验里加"渠道总量 = 账单渠道总量"对账，不平告警 |
